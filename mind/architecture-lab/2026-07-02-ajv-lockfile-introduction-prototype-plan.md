# Ajv Lockfile Introduction Prototype Plan

Date: 2026-07-02
Status: proposed governance artifact
Privacy: public-safe; no private user material included

## Architecture question

How should MC add Ajv as a dev dependency and produce the first committed `package-lock.json` while preserving the dependency-free agency runner lane?

## Decision

Do not hand-author `package-lock.json`.

Ajv may be introduced only through a package-manager-generated lockfile, because the lockfile is the provenance artifact for the resolved dependency tree. The correct first implementation is a small governance change set that is generated in a controlled environment:

1. Update `package.json` with Ajv in `devDependencies` only.
2. Generate `package-lock.json` with npm, not by manual editing.
3. Verify install determinism with `npm ci`.
4. Verify that the agency runner lane still executes without importing Ajv.
5. Add validator generation only after the lockfile exists and its hash can be recorded.

## Why this is the right boundary

The runtime agency runner must remain dependency-free. Ajv is a schema-governance tool, not runtime runner logic. This keeps the runner portable and makes schema validation a separate, auditable lane.

The current repository state has `package.json` but no committed `package-lock.json`; therefore this run should not fabricate a lockfile or pretend dependency provenance exists.

## Proposed minimal change set

### 1. Package manifest update

Add Ajv as a dev dependency:

- `devDependencies.ajv`: pinned or narrow semver range selected by the operator at install time.

Recommended first command:

- `npm install --save-dev ajv`

This updates both `package.json` and `package-lock.json` together.

### 2. Lockfile generation rule

The first lockfile must be generated by npm from the repository root. It should be committed in the same change set as the Ajv manifest update.

Required checks:

- `package-lock.json` exists at repository root.
- root lockfile `packages[""].devDependencies.ajv` matches `package.json.devDependencies.ajv`.
- lockfile contains resolved Ajv package entries under `packages`.
- `npm ci` succeeds from a clean checkout.

### 3. Runner-lane isolation check

The agency runner lane must not import Ajv. The first low-cost proof can be a static check:

- Search `tools/agency-validation/run-fixture-parity.mjs` and its direct imports for `from "ajv"`, `from 'ajv'`, or dynamic `import("ajv")`.
- Fail the agency lane if Ajv appears in runtime runner code.

A later stronger proof can use import tracing.

### 4. Governance-lane placement

Ajv can be imported only by files with explicit governance scope, for example:

- `tools/agency-validation/generate-validators.mjs`
- validator self-test files
- lockfile/provenance check files

### 5. Validator-provenance dependency

The generated validator metadata should not exist until these inputs are stable:

- schema bytes hash
- generated validator bytes hash
- `package-lock.json` hash
- Ajv package version from lockfile
- generator script hash
- isolation level: `level-1-ajv-runtime-helpers-allowed`

## Acceptance criteria

A PR/change set passes only if:

1. `package.json` and `package-lock.json` are consistent.
2. `npm ci` succeeds.
3. Ajv is present only in `devDependencies` and lockfile dev packages.
4. Runtime runner files do not import Ajv.
5. Governance docs identify Ajv as a schema-governance dependency, not a runner dependency.
6. No generated validator artifact is committed before lockfile provenance exists.

## Useful concepts extracted

- A lockfile is a source-controlled dependency-tree artifact, not just an install cache.
- `npm ci` is the clean-install verifier for committed lockfiles.
- `npm install --save-dev ajv` is the correct mechanism for updating both manifest and lockfile together.
- Ajv standalone generation belongs behind a governance seam; runtime runner code should consume generated output only after provenance exists.

## Implementation note

This artifact intentionally does not update `package.json` or create `package-lock.json` because doing so without running npm would create unverifiable dependency provenance. The correct next executable step requires a local or CI environment able to run npm against the registry and commit the generated lockfile.
